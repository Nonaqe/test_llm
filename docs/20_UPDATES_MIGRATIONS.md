# Обновления и миграции

## Краткое содержание

- Версионирование и каналы.
- Процедура обновления (пошагово).
- Правила миграций БД.
- Откат.
- Бэкапы и восстановление.
- Обновление WP-плагина и виджета.

## 1. Версионирование и каналы

- Образы: `chat-platform:<semver>`; контракт версий — SemVer (MAJOR = breaking контрактов API/widget, MINOR = фичи, PATCH = фиксы).
- Канал: `stable`. Принудительных автообновлений нет — self-hosted этика (NFR-1); проверка наличия новой версии — ручная кнопка в админке.
- Changelog поставляется с релизом (виден в админке).

## 2. Процедура обновления

```text
1. (опционально) Проверить наличие версии: админка → «Проверить обновления»
2. На сервере:
   docker compose pull
3. Pre-update бэкап: выполняется автоматически скриптом обновления
   (pg_dump -Fc + rsync uploads → volume /backups) — ОБЯЗАТЕЛЬНЫЙ шаг
4. docker compose up -d
5. api-контейнер применяет миграции: schema_migrations + advisory lock
   (одновременных применяющих нет; старые образы не конфликтуют)
6. Проверка: /widget/v1/health, страница диагностики, smoke-тест виджета
```

Рекомендация: обновлять в окно низкой нагрузки; убедиться в наличии места на диске (бэкап + новые образы).

## 3. Правила миграций БД

1. Миграции применяются автоматически при старте api (advisory lock `pg_advisory_lock`).
2. **Экспансивные и backward-compatible:** добавлять колонки/таблицы/индексы можно; удалять и переименовывать — только через 2 минорные версии (старый образ обязан работать на новой схеме — это условие отката).
3. Тяжёлые операции (переиндексация HNSW, rewrite больших таблиц) — фоновыми джобами, не в транзакции старта.
4. Каждая миграция имеет `.up.sql` и документированный `.down.sql` (там, где возможен).

Примеры — DOC-006 §8 (источник истины по стилю миграций).

## 4. Откат

| Ситуация | Процедура |
|---|---|
| Новая версия поднялась, но некорректна (схема совместима) | `docker compose` на предыдущий тег образа; схема остаётся новой (совместимой) |
| Сломана схема/данные | восстановление из pre-update бэкапа (раздел 5) + предыдущий тег |
| Откат через N версий | только через бэкап; сначала тест на копии |

Миграции «назад» автоматикой не выполняются — восстановление из бэкапа.

## 5. Бэкапы и восстановление

| Что | Как | Частота |
|---|---|---|
| PostgreSQL | `pg_dump -Fc` (сервис backup) → volume `/backups` | ежедневно (ночь) |
| Uploads | rsync → `/backups` | ежедневно |
| `.env` | копия в `/backups` (права 600) — кроме `APP_SECRET` (хранится заказчиком отдельно, см. DOC-017) | при изменении |
| Удалённая копия | опция: любой S3-совместимый endpoint, client-side шифрование | ежедневно |

Retention: 7 дневных + 4 недельных (настраивается). Кнопки «Создать бэкап сейчас» / «Скачать бэкап» — в админке.

**Восстановление (restore):**

```text
1. docker compose down (api, worker)
2. Развернуть pg_dump в чистый volume pgdata:
   pg_restore -d <new-db> /backups/unichat-2026-08-15.dump
   (скрипт restore.sh — интерактивный: выбрать файл бэкапа)
3. Восстановить volume uploads из /backups
4. Проверить .env (APP_SECRET должен быть исходным — иначе секреты не расшифруются!)
5. docker compose up -d → smoke-тест
```

Restore-процедура тестируется раз в релиз на чистой ВМ (CI/чеклист релиза, TBD).

## 6. Обновление WP-плагина и виджета

- WP-плагин: штатно через wp.org/ZIP; независимый цикл релизов; обратная совместимость по Integration Contract (DOC-007 §7).
- `widget.js`: отдаётся с `max-age=300` — обновление доезжает к посетителям за минуты; ленивые модули — immutable по хэшу.

## Чек-лист выпуска версии

- [ ] Миграции backward-compatible (удаления отложены на 2 версии)?
- [ ] Контракты /widget/v1, /api/v1 не сломаны (или MAJOR + период сосуществования)?
- [ ] Changelog подготовлен; версии в диагностике обновляются?
- [ ] Restore-тест на чистой ВМ пройден?
- [ ] Pre-update бэкап-скрипт актуален (новые volumes/таблицы)?

## Частые ошибки

- **Обновление без места на диске** — бэкап/образы не помещаются; проверять до.
- **Восстановление с новым `APP_SECRET`** — секреты настроек не расшифруются.
- **Миграция с `DROP COLUMN` сразу** — откат на предыдущий образ сломан; только через 2 версии.
- **«Откатим миграцию вручную»** — только restore из бэкапа; ручной SQL не поддерживается.
