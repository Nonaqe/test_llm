# Архитектурные решения (ADR)

## Краткое содержание

Формат каждой записи: Контекст → Решение → Альтернативы → Последствия. Статус всех — `accepted` (утверждены вместе с ADD v1.0 от 2026-08-15, если не указано иное).

## ADR-001: NestJS modular monolith (TypeScript)

- **Контекст:** нужен backend с realtime, стримингом LLM, CPU-bound воркерами, простым self-hosted деплоем; admin/widget — заведомо TS/JS.
- **Решение:** Node.js 20 + NestJS 10, modular monolith, TS везде.
- **Альтернативы:** Laravel/PHP (realtime и стриминг — экзотика; два языка), Python/FastAPI (лучшая AI-экосистема, но второй язык неизбежен), Go (незрелая AI-экосистема).
- **Последствия:** один язык и общие типы на весь продукт; CPU-bound — строго в worker; при тяжёлом парсинге — Python-sidecar через ту же очередь (V2).

## ADR-002: PostgreSQL + pgvector как единственное хранилище

- **Контекст:** нужны реляционные данные, векторы, полнотекст; установка у заказчика должна быть простой.
- **Решение:** PostgreSQL 16 + pgvector (+ tsvector), гибридный поиск RRF.
- **Альтернативы:** Qdrant (превосходно, но +1 сервис в установке каждого заказчика), Milvus/Weaviate (enterprise-избыточно).
- **Последствия:** один `pg_dump` на бэкап; транзакционное удаление чанков; интерфейс `VectorStore` оставляет путь миграции (V3).

## ADR-003: Socket.IO как единый realtime-транспорт

- **Контекст:** realtime нужен и посетителю, и операторам; важны комнаты, reconnect, fallback.
- **Решение:** Socket.IO (WS + авто-fallback на long-polling), namespace `/widget` и `/admin`.
- **Альтернативы:** «сырой» WebSocket (всё руками), SSE (однонаправленный — понадобился бы второй канал для клиентских событий), long polling (устарел).
- **Последствия:** одна транспортная модель; Redis adapter готов к масштабированию инстансов без изменения кода.

## ADR-004: Виджет — Web Component + Shadow DOM

- **Контекст:** виджет обязан не ломать сайты и не ломаться от них (NFR-4) и быть адаптивным.
- **Решение:** custom element + Shadow DOM, Preact, один ESM ≤ 60 КБ gzip.
- **Альтернативы:** iframe (максимальная изоляция, но болезненный мобильный UX и postMessage-обвязка), обычный bundle (нарушает изоляцию).
- **Последствия:** контролируемая «дырка» для темизации — CSS-переменные; iframe-режим — V2 для конфликтных сайтов.

## ADR-005: OpenAI-compatible — единственный MVP-провайдер

- **Контекст:** AI заменяем (NFR-9), но реализовывать всех провайдеров сразу нельзя.
- **Решение:** интерфейс `LlmProvider`/`EmbeddingProvider` + одна реализация OpenAiCompatibleProvider.
- **Альтернативы:** нативные SDK всех провайдеров сразу (объём без спроса), только OpenAI (ложная привязка).
- **Последствия:** один клиент покрывает OpenAI/OpenRouter/DeepSeek/Groq/Together/vLLM/LM Studio/Ollama (local LLM доступен в MVP); Anthropic/Google — V2.

## ADR-006: Docker Compose — единственный официальный деплой

- **Контекст:** self-hosted у не-сисадминов; realtime+воркеры+pgvector не живут на shared hosting.
- **Решение:** VPS + Docker Compose (caddy, api, worker, postgres, redis, backup) + installer.
- **Альтернативы:** Kubernetes (сложность неприемлема), shared hosting (технически невозможно), bare metal (невоспроизводимо).
- **Последствия:** сайты заказчика могут жить на любом хостинге — Docker нужен только chat-серверу.

## ADR-007: WP-плагин — тонкий слой

- **Контекст:** ядро платформо-независимо; WordPress — только integration.
- **Решение:** плагин = настройки + вставка того же `widget.js` + health check. Без бизнес-логики.
- **Альтернативы:** перенос логики в WP (нарушает CMS-independent core), отдельный форк виджета для WP (двойная поддержка).
- **Последствия:** независимые релизные циклы; ревью wp.org простое.

## ADR-008: Монорепо pnpm + Turborepo

- **Решение:** один репозиторий; `shared` — единственный источник контрактов; `core` — чистый TS без NestJS.
- **Альтернативы:** мультрепо (расползание контрактов), nx (избыточен).
- **Последствия:** атомарные кросс-слойные изменения; boundary-правила в CI.

## ADR-009: Visitor auth — publishable key + HMAC visitor-JWT

- **Контекст:** встраивание без секретов; при этом изоляция диалогов.
- **Решение:** publishable key при init → подписанный visitor JWT (visitor_id/site_id/project_id, 24 ч) + origin allowlist + rate limit.
- **Альтернативы:** полная анонимность без токена (нет изоляции), session-cookie (не работает на чужом origin корректно), секретные ключи на сайте (утекут).
- **Последствия:** утечка ключа некритична (regen); секретных операций у посетителя нет.

## ADR-010: Worker — отдельный процесс того же образа

- **Решение:** `api` и `worker` из одного образа, разные entrypoint'ы и лимиты памяти.
- **Альтернативы:** всё в одном процессе (блокировка event loop), отдельные образы/репо (дрейф версий).
- **Последствия:** парсинг/эмбеддинги изолированы; деплой не усложняется.

## ADR-011: Эскалация — детерминированный RulesEngine по сигналам LLM

- **Решение:** LLM возвращает confidence/интенты (валидируемая схема); решения принимают правила в коде.
- **Альтернативы:** «пусть LLM сама решает» (непредсказуемость, уязвимость к injection).
- **Последствия:** объяснимость (rule_id в handoff), тестируемость, защита от уговоров.

## ADR-012: Секреты — AES-256-GCM в БД, ключ APP_SECRET

- **Решение:** API-ключи/SMTP шифруются приложением; ключ в `.env`.
- **Альтернативы:** только `.env` для всего (нельзя менять из UI), plaintext в БД (недопустимо).
- **Последствия:** `APP_SECRET` критичен (хранить у заказчика); ротация — служебной операцией.

## ADR-013: Темизация виджета — CSS custom properties + custom_css

- **Контекст:** ручная подгонка вида чата под дизайн сайта (автоподхват отклонён как ненадёжный).
- **Решение:** три уровня: конструктор → CSS-переменные `--uni-chat-*`/поле custom_css → свой UI на Public Widget API.
- **Альтернативы:** полная свобода правки шаблонов виджета (ломает XSS-защиту/поддержку), только предустановленные темы (негибко).
- **Последствия:** изоляция сохраняется; рендер сообщений не кастомизируется на уровнях 1–2.

## Правила ведения реестра

- Новое значимое решение → новая запись ADR-NNN (контекст/решение/альтернативы/последствия, статус proposed|accepted|superseded).
- Смена решения — не редактирование старой записи, а новая со ссылкой `supersedes: ADR-NNN`.
- Обновлять связанные документы (DOC-003 и профильные).
