# Логи и мониторинг

## Краткое содержание

- Логирование (структура, уровни, редакция).
- Health-checks.
- Страница диагностики админки.
- Аудит.
- Телеметрия (opt-in).
- Типовая диагностика.

## 1. Логирование

- **pino, structured JSON** в stdout контейнеров (`docker compose logs -f api`).
- Каждый запрос — `request_id` (пробрасывается в ответы `X-Request-Id` и в ошибки 500 — по нему ищется контекст инцидента).
- Уровни: `LOG_LEVEL` из `.env` (DOC-017); production-дефолт `info`.
- **Редакция секретов:** ключи провайдера, SMTP-пароли, `APP_SECRET`, visitor-токены — никогда не логируются (redaction-слой сериализатора).
- PII: тексты сообщений в логи не пишутся; пишутся идентификаторы (conversation_id, seq) и метрики (usage токенов, latency, модель).

Ключевые события по модулям:

| Модуль | Что логируется |
|---|---|
| auth | логины (успех/провал), блокировки, refresh-ротации |
| conversations | переходы состояний (state, actor) |
| ai | вызов провайдера: модель, latency, usage, исход (ok/timeout/error) |
| rag | retrieval: кол-во чанков, best score, гейт сработал |
| knowledge | статусы документов, ошибки парсинга |
| worker | старт/ошибки джоб, ретраи |
| backup | старт/успех/ошибка, размер, путь |

## 2. Health-checks

| Endpoint | Назначение |
|---|---|
| `GET /widget/v1/health` | публичный статус (WP-плагин, uptime-мониторинг заказчика) — без деталей |
| `GET /api/v1/health` (internal) | детали для страницы диагностики: БД, Redis, очередь, провайдер |

Compose healthchecks: postgres (`pg_isready`), api — HTTP health, worker — heartbeat в Redis.

## 3. Страница диагностики (админка)

Один экран для первой линии поддержки заказчика:

- версии: образ, схема БД, WP-плагин не видно (отдельно);
- статус: БД, Redis, глубина очередей, последний successful backup;
- AI-провайдер: reachable, модель, последняя ошибка;
- счётчики за сутки: диалоги, handoff rate, ошибки провайдера;
- кнопка «выгрузить диагностический срез» (лог-хвост без секретов) — для передачи в поддержку.

## 4. Аудит (`events`)

Append-only журнал (DOC-015 §5): логины, смены настроек, regen ключей, handoff'ы, действия операторов, ошибки доступа, бэкапы. Просмотр/экспорт — админка. Записи не изменяются и не удаляются штатно.

## 5. Телеметрия

- **Opt-in, по умолчанию выключена** (NFR-1: нет обязательного phone-home).
- Отправляет: обезличенные ошибки/стек-трейсы, версию, окружение. Не отправляет: тексты диалогов, знания, ключи, домены (TBD точный состав при реализации).
- Включение/выключение — админка → Настройки.

## 6. Алерты

Email администратору (через настроенный SMTP) при: ошибке бэкапа, повторных ошибках джоб worker, недоступности AI-провайдера > N минут. Внешний uptime-пинг `GET /widget/v1/health` — средствами заказчика (рекомендация в DOC-016).

## 7. Типовая диагностика

| Симптом | Смотреть | Частая причина |
|---|---|---|
| AI не отвечает | диагностика → провайдер; логи ai | ключ/баланс провайдера, таймаут |
| Документ «индексируется» вечно | очереди на диагностике; логи worker | большая очередь/ошибка парсера в ретрае |
| Посетитель не получает пуш | логи realtime; WS в консоли | прокси режет WS → fallback (DOC-008 §8) |
| Медленные ответы | метрики ai latency + rag score | большой контекст/медленная модель |
| 500 в админке | логи по X-Request-Id | смотреть контекст request_id |

## Чек-лист новой фичи

- [ ] Новые пути ошибок логируются с контекстом (id, не тексты)?
- [ ] Секреты гарантированно не попадают в новые поля логов?
- [ ] Событие аудита добавлено для новых мутирующих действий?

## Частые ошибки

- **Логирование текстов сообщений** — PII в логах; только идентификаторы.
- **Диагностика по `docker logs` без request_id** — всегда начинать с X-Request-Id из ответа.
- **Alerty в спам без SMTP** — проверить настройку SMTP (DOC-017).
