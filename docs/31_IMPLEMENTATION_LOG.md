# Журнал реализации

## Краткое содержание

- Правила ведения журнала.
- Статусы фаз (что сделано, чем подтверждено).
- IR-записи реализационных решений («почему так в коде»).
- Реестр отложенного.

## 1. Правила ведения

1. **Обновляется в конце каждой фазы**: статусы фаз, новые IR-записи, изменения в «отложенном». Коммит журнала входит в Definition of Done фазы (DOC-030 §5).
2. **IR-формат** (implementation record — аналог ADR для решений уровня кода):

   ```text
   IR-NNN: <решение одним предложением>
   Контекст: какая проблема возникла
   Решение: что сделали
   Почему: чем выбрано
   Альтернативы: что отвергли и почему
   ```

3. **Эскалация**: если реализационное решение меняет архитектуру — сначала новый ADR в DOC-026, затем короткая ссылка сюда. IR не заменяет ADR.
4. **Отложенное** всегда содержит причину и триггер возврата.
5. IR-номера не переиспользуются; изменение старого решения = новый IR со ссылкой `supersedes: IR-NNN`.

## 3. IR-записи

### Фаза 0

**IR-001: `@uni-chat/shared` собирается в двух форматах (CJS + ESM)**
- Контекст: api (NestJS, CommonJS) и admin/widget (Vite/ESM) импортируют одни контракты; rollup админки не видел именованные экспорты enum'ов из CJS-сборки shared («ConversationState is not exported»).
- Решение: два tsconfig (`tsconfig.cjs.json`, `tsconfig.esm.json`) и `exports`-map в package.json (`import` → esm, `require`/`default` → cjs).
- Почему: один источник контрактов при любом потребителе; `core` остаётся CJS-only (его импортирует только api).
- Альтернативы: `build.commonjsOptions` в vite (хрупко, лечит симптом); ESM-only api (конфликт с NestJS/CJS-экосистемой).

**IR-002: depcruise + tsconfig-маппинг workspace-пакетов, self-test обязателен**
- Контекст: boundary-правила (DOC-004 §4) «проходили», но намеренное нарушение (core → api) не ловилось: package-name импорты резолвились в node_modules, куда depcruise не ходит.
- Решение: `.depcruise-tsconfig.json` с paths-маппингом `@uni-chat/*` на исходники; правило исключения `dist/`; проверка правил самотестом (создать пробу-нарушение → убедиться в падении → удалить).
- Почему: без маппинга guard-файл даёт ложную защищённость.
- Альтернативы: eslint-plugin-boundaries (та же проблема резолва), ручная дисциплина (не проверяется).

**IR-003: pnpm через `npm i -g pnpm@9.15.9`, corepack заблокирован**
- Контекст: `corepack enable` падал с EPERM (нет прав записи в `C:\Program Files\nodejs`).
- Решение: глобальная установка через npm (каталог пользователя).
- Почему: работает без прав администратора; версия зафиксирована в `packageManager` для CI.
- Альтернативы: запуск терминала от администратора (лишние права).

**IR-004: Dockerfile копирует структуру workspace целиком**
- Контекст: pnpm-симлинки `apps/api/node_modules → ../../../.pnpm` требуют сохранения относительной структуры.
- Решение: runtime-слой копирует root `node_modules`, `apps/api/node_modules`, `packages/`, `apps/api/dist` + `migrations/`.
- Почему: относительные симлинки продолжают указывать на цели.
- Альтернативы: `pnpm deploy` (чище, но сложнее; кандидат на пересмотр в Ф7 — IR можно supersede).

### Фаза 1

**IR-005: vitest api — swc-трансформ (unplugin-swc) вместо esbuild**
- Контекст: e2e в CI падали 500-ми: `Cannot read properties of undefined (reading 'count')` — DI Nest разворачивался в undefined.
- Решение: плагин unplugin-swc c `decoratorMetadata: true` в vitest.config.ts.
- Почему: esbuild не эмитит `design:paramtypes`, без которых конструкторная инъекция NestJS не разрешается; swc — стандартное решение.
- Альтернативы: явные `@Inject()` на каждом параметре (шум), jest+ts-jest (второй тестраннер в репо).

**IR-006: dev-режим api = `tsc --watch` + `node --watch`, tsx исключён**
- Контекст: та же причина, что IR-005 — tsx тоже esbuild-based, DI падает.
- Решение: два процесса (терминал 1 — компиляция, терминал 2 — `node --watch dist/main.js`); `dev:migrate` оставлен на tsx (там нет Nest-DI).
- Почему: единственный способ получить decorator metadata без смены сборщика.
- Альтернативы: swc-watch (дополнительная обвязка), запуск собранного вручную (медленный цикл).

**IR-007: сессии/throttling — in-memory с Redis-совместимыми интерфейсами**
- Контекст: revocation-лист refresh-токенов и brute-force buckets нужны уже в Ф1, но Redis в рантайме фазы не поднимается (CI/локаль без Docker).
- Решение: `SessionStore`/`ThrottleStore` как DI-токены; MVP-реализация `Memory*`; Redis-реализация подключается при `REDIS_URL` в Ф4/7 без изменения потребителей.
- Почему: интерфейсы сознательно повторяют Redis-семантику (TTL-записи, бакеты), подмена — одна провайдер-строка.
- Альтернативы: поднять Redis в CI уже сейчас (лишний сервис ради двух структур); хранить revocation в Postgres (лишние записи в горячем пути).

**IR-008: `events.entity_id` → text; правка миграции 0002 постфактум**
- Контекст: e2e-фол: аудит настроек передаёт строковый ключ (`ai_provider.api_key`), колонка была uuid → 22P02.
- Решение: тип text (идентификаторы сущностей неоднородны); миграция 0002 отредактирована на месте.
- Почему: правило неизменности миграций действует после первого развёртывания; на момент правки существовали только эфемерные CI-БД.
- Альтернативы: миграция 0003 с ALTER (создала бы шум истории в несуществующих инсталляциях).

**IR-009: ProjectGuard пропускает роуты без project-параметра**
- Контекст: guard стоял на уровне контроллера и бросал `AppError.internal()` на коллекционных роутах (`POST/GET /projects` без `:id`) → 500.
- Решение: нет `:projectId`/`:id` — guard пропускает; коллективная авторизация внутри обработчиков (`canInstallation`, `accessibleProjectIds`).
- Почему: per-item и collection-авторизация имеют разную природу.
- Альтернативы: перенос guard на каждый метод (шум декораторов).

**IR-010: `@node-rs/argon2` вместо `argon2`**
- Контекст: нативный `argon2` требует сборки/ABI-преbuild'ов под каждую версию Node/платформу (риск на Windows/Node 24).
- Решение: napi-rs-портированная версия с универсальными prebuilt-бинарниками; API `hash`/`verify`, argon2id по умолчанию.
- Почему: нулевая нативная сборка при установке.
- Альтернативы: `argon2` (prebuild-риски), `bcryptjs` (слабее/медленнее алгоритмически).

**IR-011: `configureApp()` — общий конвейер main.ts и e2e**
- Контекст: e2e-тесты ожидали конверт `{data}/{error}`, но фильтр/интерцептор ставились только в main.ts — тесты видели «голые» ответы.
- Решение: единая функция (префикс, cookie-parser, фильтр, интерцептор, CORS), вызывается из main.ts и из beforeAll e2e.
- Почему: тестовая среда обязана проходить тот же конвейер, что прод.
- Альтернативы: дублирование настроек в тестах (расползание конвейера).

**IR-012: cookie-политики сессии**
- Контекст: docs/15 требует httpOnly + SameSite=Lax + Secure(prod), refresh живёт 7 дней.
- Решение: access-cookie `path=/api/v1` (вся приватная зона, TTL 15 мин), refresh-cookie `path=/api/v1/auth` (отправляется только на auth-роуты), Bearer-фоллбек для не-браузерных клиентов.
- Почему: минимизация экспозиции длинного токена; фоллбек упрощает e2e/скрипты.
- Альтернативы: оба cookie на `/` (refresh летит в каждый запрос зоны).

**IR-013: setup-флоу первого владельца**
- Контекст: нужен bootstrap-пользователь до существования любого логина (docs/16 §4, docs/22 §1).
- Решение: `POST /api/v1/setup`: работает только при `users=0` и совпадении `SETUP_TOKEN` из окружения; создаёт owner и сразу выдаёт сессию; повторный вызов → 409 `SETUP_ALREADY_DONE`; попытка входа фиксируется в аудит.
- Почему: одноразовость + машинально проверяемые условия; токен знает только владелец сервера.
- Альтернативы: CLI-скрипт создания пользователя (не работает в docker-контейнере без shell-доступа у заказчика).

**IR-014: CI — DATABASE_URL на уровне шагов, не джобы**
- Контекст: env на уровне джобы включал бы e2e уже на шаге юнит-тестов — до миграций (truncate несуществующих таблиц).
- Решение: переменная объявлена на шагах «Migrations», «E2E», «Idempotent»; юнит-шаг бежит без БД, e2e-файлы в нём skipIf-пропускаются.
- Почему: изоляция шагов по окружению.
- Альтернативы: всегда-включённые e2e с ожиданием сервисов (медленнее, хрупче).

**IR-015: «Песочница» (тестовый диалог) внесена в MVP-состав**
- Контекст: проверка AI до публикации виджета нужна администратору (docs/22 §5); попала в DOC-025 как расширение состава Ф5.
- Решение: зафиксирована в roadmap; реализация — Ф5 на публичном widget-API.
- Почему: дёшево (тот же контракт), снимает главный страх запуска.
- Альтернативы: вынести в V2 (риск «настроил — не проверил — опубликовал»).

### Фаза 2

**IR-016: префиксы зон в декораторах контроллеров вместо setGlobalPrefix**
- Контекст: у системы две независимые публичные зоны с разными префиксами — `/api/v1` и `/widget/v1` (docs/07 §1); глобальный префикс Nest применил бы `/api/v1` ко всем.
- Решение: `@Controller("api/v1/auth")`, `@Controller("widget/v1")` и т.д.; `setGlobalPrefix` убран из configureApp.
- Почему: явные пути, ноль магии, зоны разведены на уровне роутинга.
- Альтернативы: exclude-патчи глобального префикса (хрупкие wildcard'ы), второй HTTP-сервер (лишний процесс).

**IR-017: visitor-JWT (Bearer) + строгий Origin-матчер**
- Контекст: встраивание без секретов при изоляции диалогов (docs/15 §1, docs/10 §4).
- Решение: HMAC-токен 24 ч (клеймы vid/sid/pid) в Authorization; Origin обязателен и матчится строго после нормализации (регистр/слэш); `*` в allowlist — явная опция сайта.
- Почему: отсутствующий Origin = отказ (не-браузерные клиенты обязаны слать заголовок) — иначе origin-защита обходится «пустым» запросом.
- Альтернативы: cookie для посетителя (чужой origin), подпись запроса HMAC (усложнение SDK).

**IR-018: идемпотентность in-memory + 404 для чужих диалогов**
- Контекст: повторная отправка при ретраях сетей; изоляция посетителей.
- Решение: Map<Idempotency-Key, message> с TTL 10 мин в процессе (Redis — Ф4 вместе с THROTTLE_STORE); обращение к чужому диалогу → 404 NOT_FOUND, не 403.
- Почему: 403 раскрывает существование диалога; 404 неотличим от опечатки.
- Альтернативы: 403 (утечка информации), уникальный индекс в БД (не решает возврат того же сообщения).

**IR-019: fake-AI — заглушка внутри WidgetService; переход NEW→AI_ACTIVE в транзакции appendMessage**
- Контекст: Фаза 2 должна быть демонстрируемой целиком без LLM (docs/30 §3).
- Решение: `scheduleFakeAiReply` (эхо через 400 мс); первый перевод NEW→AI_ACTIVE выполняется в той же транзакции, что и seq-инкремент; handoff из NEW — двойной переход (NEW→AI_ACTIVE→WAITING_OPERATOR).
- Почему: атомарность seq и состояния; заглушка живёт в сервисе и будет заменена вызовом core-Engine в Ф3 без изменения контрактов.
- Альтернативы: перевод состояния отдельным запросом (гонка с параллельным сообщением).

**IR-020: виджет рендерит только textContent**
- Контекст: содержимое ответов в Ф2 — плоский текст; любые innerHTML — XSS-поверхность.
- Решение: весь пользовательский/AI-контент — через `createTextNode`/`textContent`.
- Почему: XSS-безопасность по построению, без зависимости от санитайзера в бандле.
- Альтернативы: DOMPurify сейчас (вес ради нуля markdown-контента); появится в Ф3 вместе со стримингом markdown.

**IR-021: Redis-adapter для Socket.IO закодирован, но runtime не проверен**
- Контекст: fanout на несколько инстансов заложен архитектурой (docs/03 §7), но ни локально, ни в CI нет REDIS_URL.
- Решение: `RedisIoAdapter` подключается только при REDIS_URL; без него — штатный in-memory adapter.
- Почему: непроверенный рантайм-код не включаем молча — фиксируем как D-6.
- Альтернативы: поднять Redis в CI сейчас (сервис ради одной ветки кода) — Ф4 сделает это естественно.

**IR-022: socket.io-client в бандле виджета; polling-fallback**
- Контекст: пуш нужен сразу; WS может резаться прокси (docs/08 §8).
- Решение: socket.io-client с transports ["websocket","polling"] (встроенный fallback) + собственный интервальный добор after_seq каждые 3 с при дисконнекте; бандл 24.0 КБ gzip.
- Почему: один канал с деградацией; размер далёк от бюджета 60 КБ.
- Альтернативы: чистый WebSocket руками (свой протокол reconnect/acks), SSE (однонаправленность — отдельный канал для клиентских событий).

### Фаза 3

**IR-023: fake-провайдер — полноправная реализация интерфейсов в core**
- Контекст: CI и юнит-тесты не должны зависеть от внешнего API и денег (docs/18).
- Решение: `FakeEmbeddingProvider` — hashing-эмбеддинги (слово → измерение, нормировка): лексически похожие тексты дают высокий косинус, retrieval в e2e работает по-настоящему; `FakeLlmProvider` — детерминированный ответ из контекста + стрим по словам. Выбор — настройка `ai_provider.kind` (fake по умолчанию).
- Почему: гейт/RRF/цитаты тестируются end-to-end без сети.
- Альтернативы: мок на уровне HTTP (хрупко), скип AI-тестов в CI (дыра покрытия).

**IR-024: ingest — in-process последовательная очередь вместо BullMQ**
- Контекст: BullMQ требует Redis, которого нет ни локально, ни в CI (появляется в Ф4/7).
- Решение: очередь concurrency 1 внутри api-процесса (`KnowledgeService.enqueue`); статусы/версии/swap — как в docs/12.
- Почему: интерфейс и семантика совпадают с планом; перенос в worker — замена исполнителя.
- Альтернативы: pg-boss (очередь в Postgres — +1 абстракция), Redis в CI сейчас (сервис ради одного потребителя).
- Риск принят: рестарт в момент парсинга оставляет статус `parsing` (лечится reindex; снимается BullMQ).

**IR-025: retrieval — три запроса вместо одного CTE**
- Контекст: гибридный поиск можно одним SQL-CTE (docs/06 §5) или несколькими.
- Решение: векторный топ-20 → FTS-топ-20 → RRF-фьюжн в JS (fuseByRrf из core) → выборка топ-K с косинусом.
- Почему: RRF-логика в core тестируется юнит-без-БД; SQL проще и без дублирования.
- Альтернативы: полный CTE (быстрее на 2 запроса, но логика фьюжна в SQL и нет в core).

**IR-026: гейт = макс. косинус фьюжн-топа ≥ threshold; RRF — ранжирование**
- Контекст: у RRF-скора нет интерпретируемой шкалы (≈0.016–0.033) — «score_threshold 0.55» из схемы к нему неприменим.
- Решение: RRF выбирает кандидатов; решение «звать ли LLM» — по максимальной косинусной близости выбранных чанков.
- Почему: косинус ограничен [0,1] и семантически понятен администратору; для fake-hashing — лексическое совпадение, для реальных эмбеддингов — семантическое.
- Альтернативы: нормировка RRF-скора (искусственная шкала).

**IR-027: цитаты = все топ-K чанков; confidence от провайдера**
- Контекст: связка «ответ ↔ источник [n]» требует маппинга маркеров на чанки.
- Решение: MVP кладёт в `citations[]` весь топ-K (chunk_id + косинус); маркеры [n] в тексте остаются на совести LLM-промпта; `confidence` — из structured output (клампинг).
- Почему: без парсинга маркеров; оператор видит всю базу ответа.
- Альтернативы: парсить [n] и фильтровать цитаты (хрупко к формату ответа модели) — V2.

**IR-028: история диалога — в промпт, но НЕ в поисковый запрос**
- Контекст: docs/11 §3 обещал переформулировку вопроса по истории.
- Решение: в retrieval уходит текущий вопрос как есть; история передаётся в сообщения LLM (buildHistoryMessages).
- Почему: переформулировка = +1 вызов LLM на каждое сообщение (деньги/латентность); в Ф3 нет данных о её пользе.
- Альтернативы: LLM-переформулировка (дорого), эвристика «короткий вопрос + предыдущее сообщение» (угадывание) — обе отложены в D-9.

**IR-029: файлы знаний хранятся как `uploads/{documentId}`**
- Контекст: переиндексация (E9) требует исходник; расширение не сохранялось бы при переименовании.
- Решение: стабильное имя без расширения; тип выводится из mime/имени при парсинге; текстовые документы тоже пишутся на диск.
- Почему: reindex = чтение файла + version+1, единый путь для всех source_type.
- Альтернативы: хранить текст в БД (дублирование), сохранять расширение (рассинхрон с mime).

**IR-030: structured output — 1 fix-up-ретрай; при повторной невалиде — системное сообщение**
- Контекст: реальные модели иногда ломают JSON-схему.
- Решение: валидация (zod, клампинг) → при невалиде повтор с диагностикой причины → при повторной невалиде честное системное сообщение посетителю (не показываем сырой ответ).
- Почему: баланс устойчивости и честности; не более 2 вызовов LLM на ход.
- Альтернативы: жёсткий JSON-mode (не все совместимые endpoint'ы поддерживают), безграничные ретраи (деньги).

### Фаза 4

**IR-031: presence операторов — in-memory Map с TTL 60 с и ленивой чисткой**
- Контекст: офлайн-детект при handoff и пуш `operator:presence` нужны уже в Ф4, но Redis в рантайме по-прежнему отсутствует (D-4/D-10).
- Решение: `Map<projectId, Map<userId, expiresAt>>`; heartbeat по сокету продлевает TTL (60 с); просроченные записи удаляются лениво при чтении.
- Почему: тот же паттерн, что IR-007 (Memory-реализация за DI-интерфейсом с Redis-семантикой); перенос в Redis не меняет потребителей.
- Альтернативы: поднимать Redis сейчас (нет рантайма), хранить presence в БД (запись на каждый heartbeat).

**IR-032: переходы состояния диалога — только условный UPDATE ... WHERE state=...**
- Контекст: гонка двух операторов на accept; переданный в сервис объект строки диалога может быть устаревшим (например, диалог переоткрыт посетителем после чтения объекта).
- Решение: каждый переход выполняется условным UPDATE с проверкой текущего состояния в БД; 0 обновлённых строк → 409 `INVALID_STATE_TRANSITION`. Решение принимает БД, а не объект в памяти.
- Почему: атомарность без внешних блокировок; критерий приёмки «второй оператор получает отказ» проверяется детерминированно.
- Альтернативы: SELECT ... FOR UPDATE (длиннее транзакция), валидация по прочитанному объекту (гонка).

**IR-033: дедупликация email-напоминаний событием `handoff.email_notified` в events**
- Контекст: скан pending-handoff каждые 30 с не должен отправлять письмо по одному handoff дважды; изменения схемы не требуется.
- Решение: факт «уже уведомляли» фиксируется записью `action=handoff.email_notified` в append-only events; перед отправкой скан проверяет наличие события для данного handoff_id.
- Почему: events неизменяемы и аудируемы — один механизм даёт и дедупликацию, и историю уведомлений, без миграции схемы.
- Альтернативы: колонка email_notified_at в handoffs (миграция + второй источник того же факта), флаг в памяти (теряется при рестарте).

**IR-034: mailer за DI-токеном MAILER; консольный транспорт**
- Контекст: напоминания о pending-handoff нужны в Ф4, но SMTP-настройки и реальная отправка — задача Ф7.
- Решение: интерфейс Mailer под DI-токеном MAILER; MVP-реализация ConsoleMailer пишет в лог; SMTP-транспорт подключается в Ф7 заменой провайдера (D-11).
- Почему: потребители (скан напоминаний) не меняются; консольный транспорт наблюдаем в логах и безопасен в dev/CI.
- Альтернативы: nodemailer сразу (требует smtp.* и тестовой почты), перенести напоминания целиком в Ф7 (офлайн-сценарий Ф4 остаётся без уведомления).

**IR-035: reopen посетителем RESOLVED/CLOSED → AI_ACTIVE внутри транзакции appendMessage**
- Контекст: посетитель может написать в решённый/закрытый диалог; отдельный reopen-запрос создал бы окно между записью сообщения и сменой состояния.
- Решение: сообщение посетителя в RESOLVED/CLOSED атомарно переоткрывает диалог (→ AI_ACTIVE) в той же транзакции appendMessage; возвращаемая строка несёт state_after; движок отвечает только если state_after = AI_ACTIVE (в OPERATOR_ACTIVE/WAITING_OPERATOR молчит).
- Почему: атомарность «сообщение + состояние»; гейт ответа движка по state_after исключает ответ AI в операторских состояниях.
- Альтернативы: запрет писать в закрытые диалоги (плохой UX), отдельный endpoint reopen (гонка с параллельным сообщением).

**IR-036: RulesEngine устойчив к мусору в params; правила применяются и на ходе без LLM**
- Контекст: правила настраиваются администратором без программирования — в params возможны битый regex и нечисловой порог; часть ходов идёт без LLM (гейт-fallback Ф3).
- Решение: evaluateEscalationRules пропускает правило с невалидными params (битый regex, нечисловой порог) без исключения; RulesEngine вызывается после каждого хода, включая гейт-fallback — keyword/no_answer работают всегда.
- Почему: одна плохая строка настроек не должна ломать эскалацию; no_answer/explicit_request обязаны срабатывать и без LLM-хода.
- Альтернативы: только жёсткая валидация при сохранении (рантайм-защита всё равно нужна), применять правила только после LLM-хода (дыра в no_answer).

**IR-037: офлайн-детект по presence проекта; фразы HANDOFF_PHRASE/OFFLINE_PHRASE константами сервиса**
- Контекст: при handoff надо различать «операторы онлайн — ждите в очереди» и «все офлайн — предложим leave-email» (docs/13 §4).
- Решение: выбор ветки — по presence проекта (IR-031); прощальная и офлайн-фразы — константы HandoffService; персонализация через widget_texts — Фаза 5.
- Почему: минимальная реализация сценария Ф4; фраза уходит системным сообщением и не блокирует контракт.
- Альтернативы: таблица widget_texts сразу (нет UI редактора до Ф5), шаблоны в настройках ассистента (некому заполнить до Ф5).

**IR-038: харденинг CRUD правил — гонка ensureDefaults на 23505 и пустой PATCH**
- Контекст: ensureDefaults вызывается при первом обращении к ассистенту из нескольких мест (контроллер правил, движок хода) — параллельные запросы могут одновременно вставить дефолтный набор (unique violation 23505); PATCH правила без изменяемых полей падал SQL-ошибкой.
- Решение: вставка дефолтов перехватывает 23505 как тихий успех (`apps/api/src/escalations/escalations.repo.ts`); пустой PATCH → no-op, отсутствие правила → 404 вместо исключения.
- Почему: идемпотентность «первого обращения» не зависит от порядка запросов; внутренние ошибки CRUD не утекают клиенту как 500.
- Альтернативы: advisory lock вокруг ensureDefaults (блокировка на холодном пути), предварительный SELECT (гонку не устраняет).

**IR-039: починка бутстрапа AppModule — явные межмодульные зависимости Nest (latent-дефект с Ф3)**
- Контекст: AppModule не бутстрапился: `Nest can't resolve dependencies of the AiProviderService (... SettingsService ...)` и аналогично в других сервисах. Typecheck и vitest-юниты DI-граф не проверяют (юниты подменяют провайдеров), e2e с реальным бутстрапом локально не гонялись (нет БД) — дефект оставался невидимым с Ф3.
- Решение (`ddffcaf`): добавлены недостающие импорты модулей: RealtimeModule→AuthModule; ConversationsModule→AssistantsModule (+EscalationsModule); AiModule→SettingsModule (+exports SettingsService); AuthModule — в assistants/escalations/inbox/knowledge (для JwtAuthGuard).
- Почему: DI-граф Nest разрешается только при старте приложения; границы модулей (DOC-003 §4) должны быть объявлены явно, а не выводиться из факта инъекции.
- Альтернативы: пометить зависимые модули глобальными (размывают границы), отказаться от модульного разделения.
- Подтверждение: smoke-тест `node apps/api/dist/main.js` → /health 200 (`{"status":"ok"}`); юниты/lint/typecheck зелёные.
- Профилактика: smoke-бутстрап AppModule без БД как обязательный шаг CI — D-13, DOC-018 §5.

### Фаза 5

**IR-040: REST сайтов — точечные операции по siteId; regenerate-key = новый 24-байтный base64url-секрет**
- Контекст: docs/30 §Ф5 «projects/sites»; ключ виджета публикуется на сайтах клиента, его перезапись должна мгновенно инвалидировать старый.
- Решение: `GET/POST /api/v1/projects/:projectId/sites`; точечные операции без вложенного projectId — `PATCH /api/v1/sites/:siteId`, `POST /api/v1/sites/:siteId/regenerate-key` (ключ — 24 байта base64url, старый перестаёт работать); все операции пишут события `site.*`; пустой PATCH → 422 VALIDATION_FAILED (в отличие от no-op у правил эскалации, IR-038); изоляция: чужой siteId → 404 (неотличим от несуществующего), без права управления → 403 FORBIDDEN_PROJECT.
- Почему: siteId глобально уникален (UUIDv7) — точечный роут с одним параметром не дублирует проверку проекта (она выполняется внутри по доступным проектам).
- Альтернативы: полная вложенность `/projects/:id/sites/:sid` (длиннее, дубль проверки), регенерация через удаление+пересоздание (ломает привязку сайта).

**IR-041: аналитика MVP — производные метрики из существующих таблиц, без миграций**
- Контекст: dashboard требует метрики (диалоги/сутки, handoff rate, «разрешено AI», латентность, топ низкой релевантности), но прямых колонок для части из них в схеме Ф1 нет.
- Решение: ряды conversations/messages/handoffs по дням + totals: `ai_resolved_share` — прокси «доля диалогов без записей handoffs»; `avg_first_response_ms` — SQL-агрегат; `low_relevance_top` — assistant-сообщения с confidence < 0.5 или NULL; окно `?days=` clamp 1..90.
- Почему: прокси-метрики честны к существующей схеме (не добавляем колонки ради аналитики); clamp защищает БД от тяжёлых запросов.
- Альтернативы: колонки-счётчики в conversations (миграция + риск рассинхрона), отдельная витрина-таблица (V2).

**IR-042: песочница — полный ход движка без персистенции**
- Контекст: администратору нужно проверить AI до публикации виджета (docs/22 §5, IR-015), но тестовый диалог не должен создавать посетителей/сообщения и мусорить в аналитике.
- Решение: `POST /api/v1/projects/:projectId/sandbox/messages` прогоняет retrieval→гейт→LLM(+fix-up) в памяти; ответ с цитатами/confidence; на гейт-фолбэке — `fallback:true` с fallback-текстом ассистента; ошибка провайдера → 502 AI_PROVIDER_ERROR; в БД ничего не пишется.
- Почему: тот же код пути, что боевой ход, — песочница отражает реальное поведение виджета (критерий DOC-030 §Ф5); отсутствие записи исключает искажение метрик.
- Альтернативы: приватный настоящий диалог посетителя (мусор в данных), облегчённый endpoint без RAG (не отражает поведение).

**IR-043: просмотр sites/analytics под UseInbox — Permission ViewProject не вводился**
- Контекст: план Ф5 подразумевал право «просмотр проекта», но в RBAC-матрице core такого Permission нет (packages/core вне объёма задачи).
- Решение: чтение sites/analytics доступно участникам проекта с UseInbox (операторам), управление — ManageProject (прокомментировано в контроллерах); изоляция арендаторов сохранена (404/403).
- Почему: оператору панели сайты и аналитика нужны как контекст диалогов; расширение RBAC-core — отдельное архитектурное решение (DOC-026 при необходимости).
- Альтернативы: новый Permission ViewProject в core (выход за объём Ф5), закрыть просмотр под ManageProject (оператор теряет контекст).

**IR-044: админка — минимальные зависимости: собственный i18n-словарь, CSS-графики**
- Контекст: DOC-030 §Ф5 требует i18n ru/en и дашборд аналитики; каждая зависимость увеличивает бандл и поверхность обновлений админки.
- Решение: единственная новая зависимость — react-router-dom; i18n — собственный словарь ru/en с фолбэком locale→ru→ключ; графики dashboard — CSS-бары без chart-библиотек.
- Почему: объёмы MVP малы (словарь и бары тривиальны), зависимостная дисциплина (DOC-004 §4) важнее удобства; замена на библиотеку позже — механическая операция.
- Альтернативы: i18next + recharts (зрелее, но +вес и обновления).

**IR-045: /admin realtime — handshake по httpOnly-cookie; CORS-рефлексия убрана**
- Контекст: в Ф4 realtime inbox был выключен флагом `ADMIN_SOCKET_ENABLED=false`: сервер не отдавал access_token в теле login, а handshake Socket.IO требовал `auth.token` — пуши в панель не работали из коробки.
- Решение: (`079b392`) AdminGateway принимает JWT из httpOnly-cookie `unichat_access` на handshake (fallback к `auth.token` сохранён — e2e не тронуты), клиент подключается с withCredentials; (`2cf3a9c`) с cookie-аутентификацией отражение произвольного Origin с credentials стало CSRF-дырой (чужой сайт мог открыть сокет с cookie админа) — CORS-рефлексия на /admin убрана (`cors: { credentials: true }` без origin): панель всегда same-origin (prod) либо за dev-прокси.
- Почему: httpOnly-cookie уже является носителем сессии админки (IR-012) — дублировать токен в теле ответа ради сокета не нужно; ужесточение по модели угроз docs/15 (CSRF/credentials). Зону виджета рефлексия не угрожает — она аутентифицируется Bearer visitor-JWT (IR-017), не cookie.
- Альтернативы: возвращать access_token в теле login (расширение экспозиции токена), одноразовые socket-токены (лишний endpoint и обвязка).

**IR-046: раздача widget.js из api — путь от __dirname, env-override, кэш max-age=300**
- Контекст: сниппет из админки ссылается на `{origin}/widget.js`, но сервер отдавал 404 — по docs/05 api-контейнер обязан отдавать статику виджета.
- Решение (`3cbc133`): `WidgetJsController` (`GET /widget.js`, widget.module); файл ищется относительно `__dirname` (`<repo>/apps/widget/dist/widget.js` — работает и из src, и из dist), путь переопределяется env `WIDGET_JS_PATH`; Cache-Control max-age=300 по docs/08 §9 + кэш файла в процессе 10 с; если виджет не собран — честный 404 с подсказкой сборки. Проверено запуском: 200, text/javascript, 92 КБ.
- Почему: разрешение от `__dirname` не зависит от cwd процесса; короткий max-age соответствует политике «быстрые исправления доезжают» (docs/08 §9); 404 с подсказкой делает проблему диагностируемой вместо пустого ответа.
- Альтернативы: копирование widget.js в образ api при сборке Docker (дублирование артефакта), раздача через Caddy (вне api — ломает самодостаточность api-контейнера и локальный запуск без реверс-прокси).
