# Правила эскалации

## Краткое содержание

- Принцип: сигналы даёт LLM, решает код.
- Сигналы (вход RulesEngine).
- Типы правил и параметры.
- Режимы настройки (простой / продвинутый).
- Порядок применения и действия.
- Офлайн-поведение и таймауты.

## 1. Принцип

**Решения принимает детерминированный RulesEngine, LLM лишь поставляет сигналы** (ADR-011). Зачем: предсказуемость, объяснимость (правило видно в админке и в handoff-записи), тестируемость, защита от «уговоров» промпт-инъекций.

## 2. Сигналы (вход RulesEngine)

После каждого AI-хода LLM возвращает (валидировано сервером):

```json
{
  "confidence": 0.41,
  "user_intent_flags": { "wants_human": false, "complaint": true },
  "detected_intent": "refund_policy"
}
```

Плюс контекст: состояние диалога, наличие операторов онлайн, время ожидания.

## 3. Типы правил

Правила хранятся в таблице `escalation_rules` (упорядочены по `priority`):

| Тип | Params (пример) | Условие срабатывания | Действие |
|---|---|---|---|
| `explicit_request` | — | флаг `wants_human=true` («позовите менеджера») | handoff |
| `low_confidence` | `{"threshold": 0.55}` | `confidence < threshold` | handoff или fallback-фраза |
| `keyword` | `{"patterns": ["жалоба","скандал","суд"]}` | совпадение regex в сообщении | handoff |
| `intent` | `{"intent": "price_negotiation"}` | `detected_intent` совпал | handoff |
| `complaint` | — | флаг `complaint=true` | handoff |
| `no_answer` | `{"max_fallbacks": 2}` | N подряд fallback-ответов подряд | handoff |

Действия: `handoff` (передать оператору) | `fallback_message` (шаблонная фраза без передачи).

## 4. Режимы настройки (админка)

**Простой режим** — чекбоксы, соответствующие брифу:

```text
Когда передавать оператору:
[x] Пользователь попросил          → explicit_request
[x] AI не знает ответа              → low_confidence (threshold по ползунку)
[x] Жалоба                          → complaint
[x] Сложный вопрос                  → intent: complex_question
[ ] Запрос цены/индивидуальный расчёт → intent: price_request (выкл по умолчанию)
```

**Продвинутый режим** — редактор упорядоченного списка правил (приоритеты, параметры JSON, вкл/выкл). Пример правила:

```json
{
  "priority": 10,
  "type": "keyword",
  "params": { "patterns": ["юрист", "претензия", "верните деньги"] },
  "action": "handoff",
  "enabled": true
}
```

Дефолтный набор нового ассистента: `explicit_request` + `low_confidence(0.55)` + `complaint`.

## 5. Порядок применения

1. После AI-хода RulesEngine проходит правила **по возрастанию priority**.
2. Срабатывает **первое** подходящее правило — его действие выполняется, проверка прекращается.
3. При `handoff`: прощальная фраза AI (шаблон из widget_texts) → запись `handoffs(reason, rule_id)` → `state=WAITING_OPERATOR` → уведомление операторам.
4. `reason` и `rule_id` видны оператору в карточке диалога — объяснимость.

## 6. Офлайн-поведение и таймауты

| Ситуация | Поведение |
|---|---|
| Операторов нет онлайн в момент handoff | AI сообщает и предлагает email (офлайн-заявка) — DOC-013 §4 |
| Никто не принял за N минут (настройка, дефолт 5) | Email-уведомление операторам (SMTP) |
| WAITING_OPERATOR дольше max (настройка) | Диалог помечается «просрочен» в очереди; посетителю — повторное предложение email |
| Посетитель просит отменить оператора | `WAITING_OPERATOR → AI_ACTIVE` |

## Чек-лист изменения правил

- [ ] Понятно, какое правило и почему сработает (приоритеты не конфликтуют)?
- [ ] Порог low_confidence согласован с fallback-фразой ассистента?
- [ ] Тест RulesEngine обновлён?
- [ ] Дефолтный набор в этом документе обновлён, если менялся?

## Частые ошибки

- **Правила с одинаковым приоритетом** — порядок не определён; приоритеты уникальны.
- **Порог 0.9 «для качества»** — почти всё уйдёт операторам; подбирать по аналитике.
- **keyword-правило без границ слов** — «суд» сработает в «судя по всему»; использовать `\b`-обёртки.
- **Ожидание решения об эскалации из текста ответа LLM** — только сигналы схемы (ADR-011).
